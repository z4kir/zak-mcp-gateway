1. The problem in one minute

An AI agent uses tools (GitHub, files, databases) through MCP. The model is billed per token, which is roughly a short piece of a word. MCP wastes tokens in two places:

Before the call: the manuals. Every tool's full JSON description is sent with every request, even if the agent uses only one or two tools. GitHub alone is 3,600 tokens; GitHub plus the filesystem server is about 7,500.
After the call: the results. Asking for 10 commits returns about 18,000 tokens of JSON: avatars, API links, IDs, pretty-printing. The agent needed about 800 tokens of it, and the rest stays in the conversation for every later turn.
Analogy: You ask a hotel front desk for "a taxi". Before you can speak, they hand you the manual for every service in the hotel. When the taxi arrives, they also give you the driver's full employment file. The gateway is a good concierge: a one-page directory, a short answer, and the file stays in the back office if you ever need it.

2. The big picture

The gateway is one MCP server that the agent connects to. Behind it sit all your real MCP servers. Teal techniques (and the teal request arrows) shrink what goes into the model before a call; purple techniques shrink what comes back after it.

4. Every technique, with an everyday comparison

TechniqueWhereWhat it does (simply)Real-world analogy
Meta-toolsbeforeThe agent sees 3 tools (search, call, get_result) instead of every server's tools.One concierge desk instead of 40 service counters.
Tool indexbeforeOne line per server listing tool names, sent as server instructions. The model knows what exists without the manuals, and often skips the search.The building directory in the lobby.
Tool search (BM25)beforeFinds the right tool from plain words, with synonyms like "PR" → pull request and "ticket" → issue. Right tool in the top 3 for 32 of 32 test queries.Asking a librarian instead of reading every catalog card.
Short signaturesbeforeA long JSON schema becomes one TypeScript-style line. Parameter hints and limits are kept. Schemas too complex to shorten safely keep the full (minified) version.A recipe card instead of the cookbook chapter.
Name + argument repairbeforeAccepts github::x or x; renames per_page → perPage; turns "5" into 5; on a real mistake it returns the signature, so the next try is right.A postal clerk who fixes a misspelled street instead of returning the letter.
Exact cachebeforeThe same read with the same arguments within 5 minutes is answered from memory. Never used for writes, and any write clears that server's cache.A cafe that remembers your usual order, and forgets it when the menu changes.
Safety policybeforeRead-only mode, per-server read-only, allow and deny lists, and writes need confirm: true after the user agrees. Tools are classed read or write from MCP annotations, then verbs; unknown counts as write.A bank teller who asks for your signature before a withdrawal.
Field projectionafterKeeps only the fields asked for (project_fields), or per-tool defaults from the config. Works through lists: commit.author.name on every commit.A highlighter on a long report.
Noise + null removalafterDrops API link fields (*_url), internal IDs, and empty or null values.Throwing away junk mail before handing over the post.
Tables (TSV)afterA list of records is sent as a table, so key names appear once, not on every row. Used only when it is smaller.A spreadsheet instead of one letter per customer.
Smart clippingafterOnly when a result is too big: long text in lists is cut short; a single document keeps as much as fits.Reading the first chapters, with a bookmark for the rest.
Handles + previewafterA big result stays in the gateway. The model gets the first rows plus a handle like r3, then pages, greps, or picks fields.A coat-check ticket: your coat is safe; collect it only if you need it.
Injection warningafterResults containing text like "ignore previous instructions" are flagged as untrusted data.An "unverified sender" stamp on a note from a stranger.
Savings log + reportaroundEvery call is logged (raw vs sent tokens) to a JSONL file; npm run report recomputes totals. Live view: resource zak://stats.An electricity meter: you see what you saved.
Token budgetaroundOptional session limit: at 80% results get half the room; at 100% the gateway asks the model to wrap up.A prepaid phone plan that warns you before it runs out.
Code mode (opt-in)aroundThe model writes a short script that calls several read tools inside the gateway; only the final answer returns. Not a security sandbox, so it is off by default.Sending a runner to visit five shops and bring back one receipt.
Tool preload (agent UI)aroundThe first user message is searched up front and the best 3 signatures go into the system prompt, saving one model round trip.A waiter who brings water before you ask.
Passthrough baselinearound--passthrough runs the same servers as plain MCP, for honest before/after tests on the same scale.Weighing yourself before and after on the same scale.
Why fewer round trips matter: each time the model calls a tool, the whole conversation is sent again. A 18,000-token result read once is paid for on every later turn. Keeping it out of the conversation saves it many times over. That is why the agent-loop saving (93%) is larger than any single step suggests.

With GitHub and the filesystem server together (40 tools), tool definitions drop from about 7,500 to about 560 tokens per request (gateway's own estimate, npm run test:github).

Read these numbers honestly

  • Small setups can cost more. With 5 small tools the gateway's ~410 definition tokens exceed the ~280 of direct MCP. The gateway pays off with many tools or big results.
  • Extra round trips. Searching adds model requests (13 vs 8 here). They are cheap because the context is small, but they add latency. The tool index and tool preload let the model skip most searches.
  • Tokenizer. Counts use the o200k tokenizer as a stand-in; Claude and Gemini count a little differently, but ratios hold. The LLM-in-the-loop check (real Gemini usage numbers, both modes) is in agent-ui and needs your Gemini API key.
  • Search accuracy (32/32 in the top 3) was measured on a query set used while tuning synonyms, so treat it as a regression check, not independent proof.
  • Task success is not measured by token counts. Default projections hide fields; the handle keeps them reachable, but the agent must ask.

7. Plan coverage (Architecture & Build Plan)

PhaseStatusNotes
1. Core gatewaydoneConfig, parallel downstream connections (stdio and HTTP), catalog, search, signatures, 3 meta-tools. Client sees ~440 tokens with GitHub (target ≈ 400).
2. Result handlingdoneToken estimate, null removal, TSV, handles with paging/grep/fields/raw, projection. A 61k-token result returns 1.3k.
3. StatsdoneJSONL log (not SQLite: simpler, no dependency, recomputable), CLI report, session budget, zak://stats.
4. SafetydoneRead-only, confirm writes, allow/deny, injection warning, secrets from env.
5. BenchmarkpartialLive GitHub A/B done. Still open: 10–20 tasks over 3+ servers with a real model and success rates (the agent UI A/B mode is ready for it).
6. AdvancedpartialDone: exact cache, code mode (opt-in), tool preload, configured default fields. Not done: cheap-model router (belongs in the host app, not the gateway) and learned field pruning.

Tests use Node's built-in test runner instead of vitest, so no new dependency was added. The only new package is js-tiktoken, as a dev dependency for the benchmark.

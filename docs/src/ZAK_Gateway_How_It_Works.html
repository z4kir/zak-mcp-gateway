1. The problem in one minute

An AI agent uses tools (GitHub, files, databases, ticket systems) through MCP. The model is billed per token, roughly a short piece of a word. MCP wastes tokens in three places:

The manuals. Every tool's full JSON description goes with every request. GitHub alone is 3,600 tokens; a 227-tool company server is about 77,000.
The results. Asking for 10 commits returns ~18,000 tokens of JSON (avatars, API links, IDs). The agent needed ~800.
The turns. Every tool call is another model request that re-sends the whole conversation. Extra searches and paging multiply all of the above.
Analogy: you ask a hotel front desk for "a taxi". Before you can speak, they hand you the manual for every hotel service; when the taxi arrives they also give you the driver's employment file; and you have to walk back to the desk for every small question. The gateway is a good concierge: a one-page directory, a short answer, the file kept in the back office, and several errands handled in one trip.

2. The big picture

The gateway is one MCP server the agent connects to; all your real MCP servers sit behind it. Teal techniques shrink what goes into the model, purple ones shrink what comes back, and the grey strip makes any agent more precise and safe.

3. What is new in v0.4: seven improvements

Your company test (gateway v0.3 in front of the lean server) showed where the remaining tokens go: searches before writes (46% of result tokens) and the fixed cost of every turn (tool list + instructions, re-sent each time). v0.4 targets exactly those. Every item is generic and off by default, so v0.4 with default settings behaves like v0.3.

Workflow tools in plain words

Without a workflow (build a table with 4 columns and a rule):
create table → model turn → add column → turn → add column → turn → … → add rule → turn
~10 model turns; each re-sends the tool list and the whole conversation.
With a workflow wf__build_table:
one call with the inputs (table name, columns, rule) → the gateway runs every step in order, passes values between them (the new table's id goes into each column step), and returns one short summary.
1 model turn.
"build_table": {
  "description": "Create a table with columns and a rule. Not for editing existing tables.",
  "input": { "properties": { "table": {"type":"string"}, "columns": {"type":"array"} },
             "required": ["table", "columns"] },
  "steps": [
    { "id": "table", "tool": "lean__ap_create_table",
      "arguments": { "name": "${input.table}" } },
    { "tool": "lean__ap_create_column", "forEach": "${input.columns}",
      "arguments": { "table": "${steps.table.id}", "field": "${item}" } },
    { "tool": "lean__ap_create_rule",
      "arguments": { "table": "${steps.table.id}", "when": "before_insert" } }
  ]
}
Safety stays the sameHow
Writes need permissionOne preview of all steps; nothing runs until the agent repeats the call with confirm: true (after asking the user).
Every step is checkedEach step goes through the normal safety rules, argument checks and cache, exactly like a single call.
Failures are preciseIt stops at the first failing step and says which steps ran and which did not; a missing value never runs a step with an empty argument.
Nothing is lostEvery step's full reply is kept behind a handle; the summary is trimmed like any normal reply.
No surprisesWorkflows are written (or approved from a report suggestion) by a person, never created by the agent itself; the normal tools stay available for unusual requests.

4. What was new in v0.3

v0.2 already made each answer small. Your company test showed the next problem: extra turns. Searches and re-paging added model requests, and each one re-sends the whole conversation. v0.3 attacks turns, keeps big data out of the conversation, and makes weaker models more precise.

Fewer turns

Call tools by name from the index; compact search; most-used tools listed up front; several calls in one batch; counts and groupings computed in the gateway.
Like a shopping list: one trip, not one trip per item.

Data stays in the gateway

Write receipts instead of full echoes; $ref passes stored data into the next call; patches edit it in place; one field in full by path.
Like forwarding a parcel without opening it.

Any agent, more precise

Your rules and skills reach every client; the downstream server can ask the user or the model through the gateway; a sandboxed code mode; helpers for weak models.
Like giving every new hire the same team handbook.

7. Helping weaker models (agent UI)

Small models (Gemini Flash, Claude Haiku) lose precision when they must pick among many tools, follow long rules, plan many steps and read big results. The rule is: move decisions out of the model and into code. The test agent UI now has four switches that do this:

SwitchWhat it doesAnalogy
Preload tools + skillSearches the first question up front and puts the best signatures and any matching skill in the prompt.A waiter who brings water before you ask.
Focused toolsFor each question, the 5 best-matching tools become real functions, so the model calls them directly instead of search-then-call.Laying out only the tools for today's job.
Trim old resultsTool results from earlier turns are shortened in the history (with their handle), so they stop being re-sent in full every turn.Filing old paperwork instead of carrying it around.
Verify the answerIDs, SHAs and long numbers in the answer must appear in the tool results; otherwise the model gets one chance to correct itself.A supervisor checking the figures before the report ships.

Mind the trade-off with prompt caching (#7): "focused tools" changes the tool list on every question, so the model provider cannot reuse its cached copy of the tool list. For strong models keep it off and rely on pinned signatures; for weak models the precision gain usually matters more.

Live result (Gemini, focused + trim + verify on): "last 3 commits" used 2 model calls and called the right tool with the right arguments on the first try. A harder counting question took 47k input tokens in 10 calls, against about 110k in 12 calls for a similar question on the old gateway. The run also exposed one real gap (a path meant per row), which is fixed and now has a test.

Read these numbers honestly

  • Pinned signatures cost tokens on every turn (+100 here). They pay off only by removing searches; pin the 10–12 tools used most, not everything.
  • Best case needs the model to cooperate (call by name). With pinned signatures that is the natural behaviour, but only a live-model run proves it.
  • Workflows help multi-step jobs. On the read-only GitHub test only the overview task could use one; build tasks (like your heavy task) gain much more.
  • Read-only benchmark. Write receipts, batch writes, $ref/patch, trimming and skills are covered by 65 automated tests, not by this run.
  • Small setups can cost more than plain MCP; the gateway pays off with many tools or big results.
  • Inside Claude Code MCP is ~2.6% of all input, so whole-session savings there are small; MCP-heavy agents (your planned user agent) gain the most.
  • Tokens are not task success. The o200k tokenizer stands in for Claude/Gemini. Real-model check so far: one Gemini A/B (20,806 → 2,522 input tokens).
